# Выбор квартиры и автоматический выбор счётчиков

Дата: 2026-10-06
Ветка: `feature-place-select` (поверх `fix-ed-session-expired`, PR kostinos/hass-mosru-water#2)

## Зачем

Сейчас мастер до входа просит код плательщика (ЕПД) и номер квартиры, а после входа —
вручную указать, какой счётчик холодный, какой горячий. Оба вопроса лишние:

- после входа профиль «Электронного дома» (`profile/user/getInfo/` → `data.addresses`)
  уже перечисляет квартиры учётной записи с `fls` (код плательщика), `flat` и `userPlaceId`;
- список счётчиков (`efp/counters/listByPayerCode/`) отдаёт тип каждого счётчика в
  `typeName`: `"ХВС"` или `"ГВС"`.

Ручной ввод неудобен и приводит к ошибкам: опечатка в коде или номере квартиры, «12А»
против «12», лишний пробел — и квартира не находится.

## Объём

- Интеграция по-прежнему поддерживает одну запись (одну квартиру) на Home Assistant:
  ограничение `already_configured` остаётся.
- По-прежнему ведётся ровно одна пара счётчиков «холодная + горячая».
- Шаг выбора сенсоров HA и дня отправки не меняется.
- Повторная авторизация и «Выйти и войти заново» не меняются.

## Новый порядок шагов мастера

```
user (без формы) → qr [→ code | totp] → place → discover → sensors
```

В обычном случае (одна квартира, один ХВС и один ГВС) пользователь видит только QR,
при необходимости код подтверждения, и шаг сенсоров.

## Компоненты

### `api.py`

`MosRuClient.list_places() -> list[dict]` — квартиры из профиля ed.mos.ru.

- Источник: `GET {_ED_API}/profile/user/getInfo/`, поле `data.addresses`
  (тот же запрос, что сейчас в `find_user_place_id`).
- Элемент результата: `{"user_place_id": str, "paycode": str, "flat": str, "address": str}`.
  - `user_place_id` — `str(userPlaceId)`; записи без `userPlaceId` пропускаются.
  - `paycode` — `str(fls)` или `""`.
  - `flat` — `str(flat)`; `None` → `""`.
  - `address` — человекочитаемый адрес, если он есть в записи, иначе `""`.
- Повторы с одинаковым `user_place_id` схлопываются (остаётся первый).
- Имя поля адреса в записи `addresses` в тестовых данных отсутствует. Оно определяется
  на живом ответе до реализации (см. «Проверка на живых данных») и фиксируется в
  тестовых данных.

`find_user_place_id(paycode, flat)` переписывается поверх `list_places()`, поведение и
существующие тесты не меняются. Он по-прежнему нужен координатору: после «Выйти и войти
заново» `user_place_id` удаляется из записи и ищется заново по сохранённым `paycode`/`flat`.

`pick_counters(counters) -> tuple[str | None, str | None]` — чистая функция модуля,
выбирает `(cold_id, hot_id)` из результата `get_counters()`:

- тип сравнивается по `type` без учёта регистра и пробелов по краям;
- холодный — единственный счётчик с типом `ХВС`, иначе `None`;
- горячий — единственный счётчик с типом `ГВС`, иначе `None`.

### `config_flow.py`

`async_step_user` — без формы. Если запись уже есть → abort `already_configured`;
иначе создаёт `MosRuClient` и переходит к `async_step_qr`.

Успешный вход нового пользователя (QR без второго фактора, `code`, `totp`) ведёт в
`place` вместо `discover`. Ветка повторной авторизации (`_reauth_entry is not None`)
не меняется: обновляет cookies и перезагружает запись.

`async_step_place` (новый):

1. Однократно в executor: `authorize_ed()` и `list_places()`; результат кешируется во flow.
2. `MosRuAuthError` → abort `session_expired`.
3. `MosRuApiError` (включая временные ошибки и `HTTP 451`) → форма без полей с ошибкой
   `cannot_get_places`, текст исключения выводится через `description_placeholders`
   (`{error}`). Отправка формы повторяет шаг 1.
4. Квартир 0 → abort `no_places`.
5. Квартира 1 → выбирается без формы.
6. Квартир несколько → форма с `SelectSelector`: `value` — `user_place_id`, подпись —
   `"{address}, кв. {flat} — ЕПД {paycode}"`; пустые части опускаются
   (без адреса: `"кв. 46 — ЕПД 1344364128"`).
7. Выбранная квартира записывается в `self._data`: `CONF_USER_PLACE_ID`, `CONF_PAYCODE`,
   `CONF_FLAT`. Переход к `async_step_discover`.

`async_step_discover`:

- вход в ed.mos.ru переезжает в `place`; здесь — только `get_counters(user_place_id)`;
- `MosRuAuthError` → abort `session_expired` (как сейчас);
- `MosRuApiError` или пустой список → текущий ручной ввод ID с «Обновить список счётчиков»;
- если `pick_counters()` вернул оба ID → они записываются в `self._data`, шаг
  пропускается, переход к `async_step_sensors`;
- иначе форма выбора, где:
  - поле «холодная» содержит только счётчики `ХВС`, «горячая» — только `ГВС`;
    если для поля подходящих счётчиков нет (неизвестный или пустой `typeName`),
    в нём показываются все счётчики;
  - поле предзаполнено, если для него найден единственный подходящий счётчик.

`_discover_counters()` упраздняется: его части разносятся по `place` и `discover`.

### Переводы (`strings.json`, `translations/ru.json`, `translations/en.json`)

- `config.step.user` — удалить: шаг больше не показывает форму.
- `config.step.place` — заголовок, описание, `data.user_place_id` («Квартира»).
- `config.error.cannot_get_places` — «Не удалось получить список квартир из
  «Электронного дома»: {error}. Нажмите «Отправить», чтобы повторить.» Фронтенд HA
  подставляет `description_placeholders` шага и в тексты ошибок формы.
- `config.abort.no_places` — «В профиле «Электронного дома» нет квартир. Добавьте
  квартиру на ed.mos.ru и начните настройку заново.»

## Совместимость

- Существующие записи не мигрируются, `VERSION` остаётся 1: `paycode`, `flat`,
  `user_place_id` у них уже сохранены.
- Состав данных новой записи прежний: `paycode` и `flat` берутся из выбранной квартиры,
  поэтому имя устройства «Водосчётчик ЖКУ {paycode}» и поиск квартиры координатором
  работают как раньше.
- Устраняется ошибка текущего мастера: при ненайденной квартире запись создавалась без
  `user_place_id` (через ручной ввод ID счётчиков) и затем падала на каждом обновлении.
  Теперь `user_place_id` всегда известен до шага счётчиков.

## Тесты

`tests/test_api.py`:
- `list_places`: числа → строки, `flat: None` → `""`, пропуск записей без `userPlaceId`,
  схлопывание повторов, адрес из живого ответа, пустой профиль → `[]`;
- существующие тесты `find_user_place_id` остаются зелёными;
- `pick_counters`: 1 ХВС + 1 ГВС; два ХВС + один ГВС; неизвестные типы; пустой список;
  регистр и пробелы в `typeName`.

`tests/test_reauth.py` (или новый `tests/test_place_flow.py` с тем же загрузчиком методов):
- `user` сразу ведёт к QR; при существующей записи — abort `already_configured`;
- успех QR / `code` / `totp` без повторной авторизации ведёт в `place`;
- повторная авторизация по-прежнему обновляет запись и не заходит в `place`;
- `place`: 0 → abort `no_places`; 1 → без формы, данные записаны; несколько → форма с
  подписями; `MosRuApiError` → форма с ошибкой и текстом; повторная отправка повторяет
  запрос; `MosRuAuthError` → abort `session_expired`;
- `discover`: автопропуск при паре ХВС/ГВС; фильтрация и предзаполнение; ручной ввод при
  ошибке;
- переводы: шаг `place`, ошибка `cannot_get_places`, abort `no_places` во всех трёх файлах;
  шага `user` в переводах нет.

## Проверка на живых данных

Мастер добавления на рабочем HA запустить нельзя без удаления настроенной записи (это
потеряет историю сенсоров). Поэтому до реализации разбора адреса:

1. Временно (с пометкой `DEBUG-TEMP`) записать в журнал при обычном обновлении
   интеграции только **имена ключей** записей `data.addresses` и вложенного адреса, а
   также множество значений `typeName` из `listByPayerCode`. Значения полей в журнал не
   пишутся.
2. По результату зафиксировать имя поля адреса и тестовые данные, удалить диагностику.

Полный прогон мастера добавления на живом HA — только по решению владельца HA
(требует удаления и повторного добавления интеграции).
